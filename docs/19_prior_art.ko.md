# 19. 선행 도구와 Reqover의 자리

"이런 건 아무도 안 한다"는 주장은 들여다볼수록 약해집니다. 그래서 이 문서가 대신 들여다봅니다. Reqover 주변을 이미 차지하고 있는 도구들을 나열하고, 각각이 무엇에 답하는지 적고, Reqover가 답이 아닌 경우를 그대로 밝힙니다.

요약하면 이렇습니다. 성숙한 도구 여럿이 **코드와 테스트**를 연결합니다. Reqover는 **코드와 관측된 HTTP 요청**을 연결합니다. 단어 하나 차이지만, 그 결과로 할 수 있는 일이 달라집니다.

## 각 도구가 답하는 질문

| 도구 | 귀속 단위 | 정밀도 | 답하는 질문 |
| --- | --- | --- | --- |
| [JaCoCo](https://www.jacoco.org/jacoco/) | 없음 (누적 집계) | 라인, 분기 | 이 라인이 무엇에 의해서든 실행되긴 했는가? |
| [OpenClover](https://openclover.org/) | 테스트 케이스 | 라인 | 어떤 **테스트**가 이 라인을 실행했는가? |
| [Datadog Test Impact Analysis](https://docs.datadoghq.com/tests/test_impact_analysis/) | 테스트 케이스 | 파일 | 이 커밋에서 어떤 **테스트**를 건너뛸 수 있는가? |
| 상용 quality-intelligence 제품군 | 테스트 케이스 | 라인/메서드 | 이 변경을 어떤 테스트가 덮는가, 테스트 공백은 어디인가? |
| APM / 분산 트레이싱 | 요청 (트레이스) | 계측된 경계 | 이 요청은 어디서 시간을 썼고 무엇이 실패했는가? |
| 트래픽 리플레이 | 기록된 요청 | 요청/응답 | 새 빌드가 예전 트래픽에 여전히 같은 답을 주는가? |
| **Reqover** | **관측된 HTTP 요청** | **메서드 진입** | **어떤 엔드포인트가 이 코드를 실행했는가?** |

## 가장 가까운 이웃들

### OpenClover — 제일 가까운 친척

OpenClover는 테스트 케이스 단위로 커버리지를 기록하고 "이 라인을 어떤 테스트가 지나갔는가"에 답할 수 있습니다. 수동 테스트용 recorder를 쓰면 사람이 직접 조작하는 구간에 이름 붙인 기록을 열 수도 있습니다. 오픈소스이고, 성숙했고, 라인 단위라 Reqover의 메서드 진입보다 정밀합니다.

그래도 단위는 여전히 **테스트**입니다. 기록은 누군가 시작하고 이름을 붙여야 하고, 기록을 `GET /orders/{id}`에 저절로 묶어 주는 장치는 없으며, Reactor의 thread hop을 넘어 기록을 이어 주지도 않습니다. 동시에 처리 중인 요청들을 따로 귀속시키는 문제를 애초에 풀려던 도구가 아니기 때문입니다. 계측도 소스 레벨이라 빌드에 손을 넣어야 하지만, Reqover는 이미 빌드된 JAR에 붙습니다.

질문이 "내 JUnit 테스트 중 어떤 게 이 클래스를 건드리나"라면 OpenClover를 쓰세요. 그건 Reqover가 앞으로도 이기지 못할 영역입니다.

### Datadog Test Impact Analysis와 상용 quality-intelligence 제품군

"test impact analysis"를 하나의 카테고리로 만든 도구들입니다. 테스트별 커버리지를 수집해 백엔드에 저장하고, 커밋이 영향을 줄 수 없는 테스트를 실제로 건너뛰는 데 씁니다. Reqover보다 완성된 제품이고, 대신 비공개 소스이며 그에 맞는 가격이 붙습니다.

Reqover와 겹치는 부분은 *역인덱스*라는 발상입니다. 다른 부분은 역시 단위와 데이터 출처입니다. 이들의 인덱스는 **당신의 테스트 스위트**에서 만들어지므로 가치가 테스트 커버리지에 묶입니다. Reqover의 인덱스는 **누군가 실제로 보낸 트래픽** — QA 세션, 스테이징 부하, 통합 테스트 실행 — 에서 만들어지므로, 아직 어떤 자동화 테스트도 덮지 않는 코드 경로에 대해서도 말할 수 있습니다. 그리고 그게 동시에 약점이기도 합니다(아래 참고).

### APM과 분산 트레이싱 (Pinpoint, Jaeger, Elastic APM, Datadog APM)

이건 정직하게 비교해야 하는 상대입니다. 트레이싱도 요청 단위이고 Java agent를 쓰며, 닮은 건 실제로 닮았습니다.

트레이싱은 **경계**를 계측합니다. 들어온 요청, 데이터베이스 호출, 외부 HTTP 호출 같은 지점에서 span을 만들고, 그 결과는 타임라인으로 읽히도록 설계됩니다. 그리고 대개 샘플링합니다. 운영 환경의 모든 트레이스를 보관하는 건 비싸기 때문입니다. 제품이 답하려는 질문은 "왜 느린가, 무엇이 실패했는가"입니다.

Reqover는 **지정한 패키지의 모든 메서드 진입**을 계측하고, 타임라인을 남기지 않으며, 기록 구간 안에서는 아무것도 샘플링하지 않습니다. 산출물은 집합입니다. 이 요청이 지나간 메서드들의 집합. 집합은 뒤집을 수 있고, 그게 핵심입니다. 타임라인은 "어떤 엔드포인트가 이 클래스에 닿는가"로 뒤집히지 않습니다. Reqover가 운영에 상주하는 대신 개발·QA·스테이징을 겨냥해 만들어진 것도 그래서입니다. 전부 기록하는 게 감당 가능한 환경이라는 뜻입니다.

엔드포인트가 왜 느린지 알고 싶다면 트레이싱을 쓰세요. Reqover는 그걸 알려 주지 않습니다.

### 트래픽 리플레이 (Arex, Diffy, GoReplay)

리플레이 도구는 운영 트래픽을 잡아 두었다가 새 빌드에 다시 흘려보내 응답을 비교합니다. "테스트 스위트보다 실제 트래픽이 나은 증거"라는 감각은 Reqover와 같지만, 답하는 질문이 다릅니다. *동작이 바뀌었는가*이지 *무엇부터 봐야 하는가*가 아닙니다. 둘은 경쟁하기보다 겹쳐 쓰기 좋습니다. 리플레이 실행이야말로 Reqover로 기록해 둘 만한 트래픽입니다.

## 실제로 새로운 것

이미 존재하는 걸 전부 걷어내면 세 가지가 남습니다.

1. **귀속 단위가 테스트 케이스가 아니라 살아 있는 HTTP 요청입니다.** 여기가 하중을 받는 차이입니다. 역인덱스가 스위트가 검사하는 것이 아니라 시스템이 하는 일을 반영하게 되고, 결과가 *엔드포인트* 목록으로 나옵니다. 리뷰어, QA 엔지니어, API 테스트 계획이 실제로 소비하는 형태가 그겁니다.
2. **귀속이 reactive thread hop을 넘어 살아남습니다.** 위에서 언급한 단위별 커버리지 도구들은 모두 단위가 thread를 소유한다고 가정합니다. WebFlux는 그 가정을 깹니다. Reqover는 Micrometer context propagation을 통해 Reactor `Context`로 bucket을 실어 나르므로, `boundedElastic`으로 넘어간 요청도 자기 bucket에 기록됩니다. WebFlux에서 요청 단위 커버리지 귀속을 하는 오픈소스 도구는 아직 찾지 못했습니다.
3. **인덱스를 JVM 없이 파일에서, CI에서 조회할 수 있습니다.** 내보낸 리포트에는 클래스·메서드 이름이 그대로 담기므로 `reqover impact`가 파이프라인에서 읽어 diff를 재검증할 엔드포인트 목록으로 바꿉니다. Pull Request 코멘트로든, exit code로든.

새로운 건 조합입니다. 개별 재료 — bytecode 계측, 단위별 커버리지 bucket, context 전파, 역인덱싱 — 는 모두 확립된 작업이고, 그렇지 않은 척하면 프로젝트가 더 나빠질 뿐입니다.

## Reqover를 쓰지 말아야 할 때

- **라인이나 분기 정밀도가 필요할 때.** Reqover는 메서드 진입을 기록합니다. JaCoCo를 쓰시고, 대체가 아니라 나란히 쓰세요.
- **질문이 엔드포인트가 아니라 테스트에 관한 것일 때.** OpenClover와 상용 test impact 제품들이 그걸 위해 만들어졌고 더 잘합니다.
- **운영 관측이 필요할 때.** APM을 쓰세요. Reqover는 개발·QA·스테이징 도구입니다.
- **변경이 안전하다는 보증이 필요할 때.** Reqover가 보고하는 건 관측된 실행에서 나온 *하한*입니다. 대조되지 않은 파일은 "관측된 실행 없음"으로 보고되며, 이는 "본 적 없음"이지 "영향 없음"이 아닙니다. 정적 호출 그래프는 한 번도 실행되지 않은 코드에 대해서도 주장하지만, Reqover는 의도적으로 하지 않습니다.

## 도움을 받고 싶은 열린 질문

- reactive 스택에서 요청 단위 커버리지 귀속을 하는 오픈소스 도구를 저희가 놓친 게 있나요? 이슈로 알려 주세요. 없는 공백을 있다고 주장하느니 그 도구를 인용하는 편이 낫습니다.
- 샘플보다 훨씬 큰 코드베이스에서도 역인덱스가 계속 쓸모 있을까요? 아직 모릅니다. 실제 저장소와 부딪혀 봐야만 답이 나옵니다.
