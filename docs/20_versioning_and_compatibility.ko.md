# 20. 버전, 호환성, 롤백

Maven Central 배포는 영구적입니다. 한 번 릴리스된 버전은 바꿀 수도 내릴 수도 없으므로, 버전 번호에 붙는 약속은 첫 업로드 *이전에* 존재해야 합니다. 이 문서가 그 전제 조건입니다.

버전 번호가 무엇을 약속하는지, 무엇이 공개 API인지, 지원하는 Java·Spring 버전이 어떻게 움직이는지, 그리고 릴리스가 잘못됐을 때 무슨 일이 일어나는지를 다룹니다.

## 좌표

모든 모듈은 `io.reqover` 그룹으로 배포되며 버전을 공유합니다.

| 좌표 | 이럴 때 쓰세요 |
| --- | --- |
| `io.reqover:reqover-spring-boot-starter` | Spring Boot 애플리케이션이 있을 때. 여기서 시작하면 필요한 것을 알아서 끌어옵니다. |
| `io.reqover:reqover-core` | `CoverageStore`를 직접 구현하거나 `UnitScope`를 직접 열 때. |
| `io.reqover:reqover-report` | 리포트를 코드로 읽고, 렌더링하고, 비교하고, 분석할 때. |
| `io.reqover:reqover-spring-mvc` / `-spring-webflux` | starter 대신 어댑터를 직접 배선할 때. |
| `io.reqover:reqover-instrumentation` | ASM transformer 위에 직접 무언가를 만들 때. |
| `io.reqover:reqover-agent` | `-javaagent` JAR. 보통 의존이 아니라 내려받아 씁니다. |
| `io.reqover:reqover-cli` | 릴리스 JAR 대신 빌드에서 `render`·`diff`·`impact`를 돌릴 때. |

모든 모듈은 같은 버전으로 나갑니다. `io.reqover` 모듈 간 버전을 섞는 것은 지원하지 않으며 테스트하지도 않습니다.

## 버전 번호가 약속하는 것

Reqover는 [유의적 버전](https://semver.org/lang/ko/)을 따르되, 1.0 이전 규칙을 명시합니다. "0.x는 뭐든 바뀔 수 있다"는 명세상 맞는 말이지만 실무에서는 아무 쓸모가 없기 때문입니다.

### 버전이 `0.`으로 시작하는 동안

- **패치** (`0.2.0` → `0.2.1`) — 공개 API 변경 없음. 아무것도 읽지 않고 올려도 안전합니다. 버그 수정, 성능, 문서, 의존성 갱신.
- **마이너** (`0.2.x` → `0.3.0`) — **공개 계약을 깰 수 있습니다.** 모든 파괴적 변경은 [CHANGELOG.md](../CHANGELOG.md)의 `Breaking` 항목에 마이그레이션 방법과 함께 적습니다. 마이그레이션 한 줄을 쓸 수 없다면 그 변경은 나가지 않습니다.
- 이전 릴리스에서 deprecated 표시를 거치지 않은 것을 마이너에서 제거하지 않습니다. **예외는** 그것이 두 마이너 릴리스보다 어리거나, 유지하는 것이 명백히 잘못된 것을 계속 배포하는 일이 될 때뿐이며, 두 경우 모두 `Breaking` 항목에 기록됩니다.

### `1.0.0` 이후

- 파괴적 변경은 **메이저**, 추가는 **마이너**, 수정은 **패치** — 일반 규칙 그대로.
- 메이저에서 제거되는 것은 최소 한 번의 마이너 릴리스에서 먼저 deprecated 되며, 대체재는 그 시점에 이미 존재합니다.

`1.0.0`은 일정이 아닙니다. 아래 공개 계약이 우리 것이 아닌 코드베이스와 부딪혀 살아남았고, 이제 그만 바꾸겠다고 말할 수 있게 되는 지점입니다. 그전까지 `0.` 접두사는 정직하게 제 역할을 합니다.

## 무엇이 공개 API인가

호환성 약속은 정확히 이 목록만 덮습니다.

- **`reqover-core`** — `CoverageStore`, `UnitScope`, `UnitInfo`, `CoverageBucket`, `CoverageBucketSnapshot`, `CoverageContext`, `ReqoverProbe.hit`
- **설정 프로퍼티** — 문서화된 모든 `reqover.*` 프로퍼티
- **내보낸 리포트 JSON** — 아래 스키마 규칙 참고
- **`reqover-cli`** — 명령 이름, 플래그 이름, 출력 형식, exit code (`0` 정상, `1` 게이트 작동, `2` 잘못된 사용 또는 입력)
- **agent 옵션 문자열** — `-javaagent:reqover-agent.jar=include=...`
- **composite GitHub Action** — 입력 이름과 그 의미
- **`reqover-report`** — 리포트 모델 타입과 렌더러

그 외는 Java 가시성과 무관하게 전부 내부 구현이며 어떤 릴리스에서든 바뀔 수 있습니다. 이 목록에 없는 것에 의존하고 있다면 이슈를 열어 주세요. 목록이 틀렸다는 신호이고, 예고 없이 여러분을 깨뜨리느니 목록을 고치는 편이 낫습니다.

`ReqoverProbe.resetGlobalStateForTests`는 agent가 클래스 로더를 넘어 호출해야 해서 public이지만 공개 API가 아닙니다. 실행 중인 애플리케이션에서 호출하면 agent가 등록한 메타데이터가 영구히 사라집니다.

### 리포트 JSON 스키마

내보낸 리포트는 `schemaVersion` 필드를 가지며 현재 값은 `1`입니다. 읽기 규칙은 다음과 같습니다.

- **새 선택적 필드는 패치를 포함해 어떤 릴리스에서도 추가될 수 있습니다.** 읽는 쪽은 모르는 필드를 무시해야 합니다.
- **`schemaVersion`이 없는 문서는 버전 1로 읽습니다.** 지금까지 존재한 형태가 그것뿐이기 때문입니다.
- **더 새로운 스키마의 문서는 버전을 명시한 오류와 함께 거부합니다.** 조용히 잘못 해석되는 것보다 낫습니다. 리포트는 한 잡이 쓰고 다른 잡이 읽으며, 둘은 같은 순간에 업그레이드되지 않습니다.
- **같은 스키마 버전 안에서 필드가 제거되거나 의미가 바뀌는 일은 없습니다.**
- **파괴적 스키마 변경은 `schemaVersion`을 올리고**, CLI는 최소 한 마이너 릴리스 동안 이전 버전을 계속 읽습니다. 업그레이드 전에 기록한 리포트가 업그레이드 후에도 분석되도록 하기 위해서입니다.

## 지원하는 Java·Spring 버전

| | 현재 |
| --- | --- |
| 빌드용 JDK | 17, 21 |
| bytecode 대상 | Java 17 |
| 실행용 JDK | 17 이상 |
| 검증된 Spring Boot | 3.5.x |

- CI에 JDK나 Spring Boot 라인을 **추가**하는 것은 마이너 릴리스입니다.
- **제거**하는 것은 `1.0.0` 이전에는 마이너, 이후에는 메이저이며, 어느 쪽이든 CHANGELOG에 공지합니다.
- bytecode 대상은 마이너(1.0 이전) 또는 메이저(1.0 이후)에서만 올라갑니다. 패치에서는 움직이지 않습니다.

검증하지 않은 Spring Boot 버전이 반드시 깨진다는 뜻은 아닙니다. 테스트하지 않았다는 뜻입니다. 되더라, 안 되더라 하는 보고 모두 유용한 기여입니다.

## 릴리스가 잘못됐을 때

Maven Central은 불변입니다. 배포 취소도, yank도, 릴리스된 아티팩트 수정도 없습니다. 그래서 "롤백"이 무언가를 없애는 일이 될 수 없습니다. 여기서 롤백은 이런 뜻입니다.

1. **빠르게 앞으로 고칩니다.** 잘못된 버전은 Central에 영원히 남습니다. 답은 그것을 대체하는 패치 릴리스이며, 진행 중인 무엇보다 우선해서 냅니다.
2. **잘못된 릴리스를 표시합니다.** 해당 버전의 GitHub Release에 문제와 대신 쓸 버전을 눈에 띄게 적고, [CHANGELOG.md](../CHANGELOG.md)의 수정 버전 항목에 기록합니다.
3. **공개적으로 알립니다.** 증상, 영향받는 대상, 우회 방법을 적은 이슈를 고정하고 수정 릴리스가 나올 때까지 열어 둡니다.
4. **빠진 테스트를 추가합니다.** CI가 잡지 못한 방식으로 깨진 릴리스는 게이트에 구멍이 있었다는 뜻입니다. 그 구멍은 "나중에"가 아니라 수정과 같은 PR에서 막습니다.
5. **정말 필요할 때만 회수합니다.** 배포되어서는 안 되는 것 — 비밀값이거나, 배포할 권리가 없는 코드 — 이 들어간 경우에는 Central 지원팀에 삭제를 요청하고 그 사실을 공개합니다. 최후의 수단이며 롤백 수단이 아닙니다.

배포는 됐지만 공지하지 않았고 알려진 다운로드가 없는 버전에도 같은 규칙을 적용합니다. 릴리스가 없었던 척하지 않습니다.

## 첫 Central 배포 전에

배포는 아래가 모두 참이 될 때까지 의도적으로 비활성 상태이며, 이 체크리스트가 [#4](https://github.com/reqover-labs/reqover/issues/4)의 수용 기준입니다.

- [x] 이 문서가 존재하고, 여기 적힌 약속이 우리가 지킬 수 있는 것들이다
- [x] 위 공개 API 목록이 코드가 실제로 노출하는 것과 일치한다
- [x] 리포트 JSON이 `schemaVersion`을 담고, 읽는 쪽이 더 새로운 스키마 문서를 잘못 해석하는 대신 거부한다
- [ ] 서명된 스테이징 번들 dry-run (`REQOVER_SIGNING_KEY=... ./gradlew centralBundle`) — 파이프라인은 존재하고 서명 없는 번들은 정상 생성되지만, 키를 넣고 돌린 적은 없다
- [ ] Central Portal에서 `io.reqover` 네임스페이스를 검증하고 `PUBLISH_TO_MAVEN_CENTRAL`을 활성화한다
- [ ] 소비자 스모크 테스트: 이 저장소 바깥의 프로젝트가 Central에서 starter를 받아 요청 하나를 기록한다

마지막 항목은 형식적인 절차가 아닙니다. 이 빌드 바깥의 누구도 받아 본 적 없는 starter를 배포하는 것이야말로 영구적인 실수가 만들어지는 경로입니다.
