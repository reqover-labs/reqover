# OSV 보안 검사 실패 보완

최초 확인일: 2026년 10월 4일, 갱신일: 10월 6일. Jackson·Tomcat 패치는
[PR #26](https://github.com/reqover-labs/reqover/pull/26)으로 main에 반영됐습니다.
#25는 이제 문서만 추가하며 이미 배포한 0.2.0 파일은 자동으로 바뀌지 않습니다.

## 현재 남아 있는 보안 항목

최신 main 동기화 전 10월 6일 [GitHub 검사](https://github.com/reqover-labs/reqover/actions/runs/37428486980/job/112154025632)와
외부 Maven 항목 104개를 전부 조회한 로컬 검사에서는 Spring MVC 6.2.19의
[GHSA-pc63-qcmh-9cmg](https://github.com/advisories/GHSA-pc63-qcmh-9cmg)가 확인됩니다.
10월 5일 갱신된 항목이며 아래의 Jackson·Tomcat 경고와는 별개입니다.
10월 4일에 알려진 취약점이 0개였다는 결과를 지금도 0개인 것처럼 해석하지 않습니다.

[Spring 공식 공지](https://spring.io/security/cve-2026-47884/)는 특정 XsltView 설정에서
발생하는 문제와 수정판을 설명합니다. 6.2.20은 상용 지원 전용이고 공개 수정판은
7.0.9입니다. 모든 MVC API가 바로 공격당한다는 뜻은 아니지만, 데모에서 해당 설정을
안 쓴다는 이유만으로 의존성이 패치됐다고 볼 수도 없습니다.

정식으로 지원되는 수정된 6.2 계열을 사용할지, Spring·Boot 전체 호환성을 검증하며
공개 지원 계열로 옮길지 별도 보안 작업에서 결정해야 합니다. Boot 3.5 앱에 MVC만 7로
강제 변경하지 않습니다.

이후 main `935d3db`에 유지관리자가 정한 `osv-scanner.toml` 정책이 반영됐습니다.
해당 경고만 2026년 12월 31일까지 예외로 두며, XsltView를 쓰지 않는 데모·테스트 환경과
사용자 앱이 직접 Spring 버전을 선택하는 구조를 근거로 명시합니다. 이번 동기화는 그
기존 정책을 보존하며 예외 범위를 늘리지 않습니다. 정책을 적용한 CI는 통과할 수 있지만
라이브러리 자체가 패치된 것은 아닙니다. `findings`와 `exceptions`를 구분해서 읽습니다.

## 왜 빨간색이었나

GitHub가 고장 난 것이 아니라, 의존성 목록 검사에서 **취약 패키지 3개와 취약점
10개**가 발견되어 보안 정책대로 실패한 것입니다. 소스 기능 테스트를 통과해도
외부 라이브러리가 취약하면 이 검사는 실패할 수 있습니다.

| 대상 | 기존 | 변경 |
| --- | --- | --- |
| Jackson core·databind | 2.21.5 | 2.21.7 |
| Tomcat core·EL·WebSocket | 10.1.55 | 10.1.60 |

Jackson은 기존 2.21 계열의 보안 패치로 맞췄습니다. Tomcat도 10.1 계열을 유지하고
MVC 데모와 starter 테스트에서만 버전을 맞춥니다. 실제 사용자 앱의 서버 의존성을
강제로 바꾸거나 agent·요청 귀속·리포트 형식을 고치는 작업은 아닙니다.

Tomcat 공지의 수정 버전 10.1.58은 배포 투표가 통과하지 않아 내려받을 수 없습니다.
그래서 실제 배포된 10.1.60을 선택했습니다. 스캐너의 “고칠 수 있는 취약점 0개”
문구만 믿지 않고, 유지관리자의 수정 범위와 배포 저장소를 직접 확인했습니다.

## 무엇을 확인하나

의존성을 바꾼 뒤 Gradle이 실제 선택한 버전으로 SBOM을 다시 생성합니다. 숫자만
수정하지 않고 해시와 관계까지 함께 갱신합니다. 로컬 OSV 재조회에서는 외부 Maven
항목 104개 전체를 검사해 **당시에는 3개에서 0개**가 됐습니다. 현재 결과는 위 항목과 구분합니다.

보안 검사는 계속 켜져 있습니다. 위의 기존 정책 외에 새 예외를 넣거나 실패를 숨기거나
보안 작업에 `continue-on-error`를 추가하지 않습니다. 전체 동작과 GitHub 결과까지
확인한 뒤 완료로 판단합니다. 상세 취약점과 재현 명령은
[영문 기록](29_osv_dependency_remediation.md)에 있습니다.

윈도우에서 예전 데모 서버가 JAR을 잡고 있으면 `clean`이 삭제 오류로 실패할 수
있습니다. 이 경우 실행 중인 데모를 강제로 끄지 않고 깨끗한 검증 폴더를 사용합니다.

“지금 알려진 취약점이 0개”라는 결과는 모든 보안 위험이 없다는 뜻은 아닙니다.
사용자 앱도 자체 의존성과 인증·접근 정책을 계속 관리해야 합니다.
