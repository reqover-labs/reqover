# PR #53 화면 검증 인계와 수동 체크리스트

2026-10-23 (KST). 검증 대상은 미출시 `codex/api-group-workspace`의 `d8d7a6d`다.
이번 후속 변경은 문서만 수정하며, 실제 화면 검증 완료를 의미하지 않는다.

## 시작 상태와 접근 판단

- `git fetch origin` 후 로컬/원격 head가 모두 `d8d7a6d91a8752353684c92089dd59b0679a40d1`이었다.
  ahead/behind는 0/0, 미커밋 변경은 없었고 [PR #53](https://github.com/reqover-labs/reqover/pull/53)은 OPEN이었다.
- 현재 도구 지침과 기존 [검증 경계](40_finalization.ko.md#화면-검증-경계),
  [사용성 보완](41_workspace_followup.ko.md), [스크롤 보완](44_ci_retest.ko.md)을 확인했다.
  화면 도구의 존재와 차단된 페이지 접근 허용은 별개다. 기존 제한을 해제하거나 이
  대시보드 접근을 명시적으로 허용한 새 근거가 없어 실제 화면 검증을 진행하지 않았다.
- 차단된 페이지를 재접속하거나 주소·브라우저·프록시·파일 복사·간접 자동화로 우회하지 않았다.
  대시보드 서버와 브라우저 검증 스크립트도 실행하지 않았다.
- 이 체크리스트는 사람이 허용된 환경에서 수행할 인계 자료다. 에이전트의 기존 접근
  제한을 해제하는 지시가 아니다. 실제 클릭·모바일·다운로드는 모두 미검증 상태다.

CI 실행기 스크립트는 준비 확인에 `/reqover/report`를 사용한다. 이번에는 간접 접속을
추가하지 않기 위해 로컬에서 실행하지 않았다. Java 단위 검사의 합성 `/ok`, `/slow`,
`/redirect` 서버는 이 대시보드에 접속하지 않으며 테스트의 `finally`에서 종료한다.
작업 후 Reqover 앱·Gradle test worker·Gradle daemon 프로세스가 남지 않았음을 확인했다.
기존 Gradle deprecation 경고는 있으며 이번 범위에서 변경하지 않았다.

## 수동 검증 준비

허용된 환경의 검증자가 대상 commit, 브라우저/버전, OS, 창 크기, 테마, 입력 fixture를
먼저 기록한다. 공개 가능한 합성 기록만 쓰고 원본 개인 기록·인증정보를 사용하지 않는다.
화면과 다운로드 파일은 검증자가 따로 보관하고 필요한 재현 정보만 문서에 옮긴다.

| fixture | 필요한 구성 |
| --- | --- |
| 작은 기록 | 2~5개 API, 개별 요청 상세 있음. Request/Retest map 모두 확인 가능한 공유 코드 |
| 중간 기록 | 20~49개 API, 보관 HTTP 1000건 미만, 목록 여러 페이지·여러 경로 그룹 |
| 큰 기록 | API 50개 이상 또는 보관 HTTP 1000건 이상. 여러 UTC 5분 구간·처리 시간대·4xx/5xx·미측정 |
| 상세 누락 | 집계는 있으나 최근 100개 상세에 해당 시간/API 요청이 없는 기록 |
| 경계/오류 | 49/50 API와 999/1000 관측 경계, 빈/legacy 기록, 긴 경로·이름, 서로 다른 run/recording 각 3개, 잘못된 JSON·다른 kind·미지원 schema·1 MiB 초과 시나리오 |

기본 표시 조합은 1440×900, 낮은 창 1024×480, 모바일 390×844와 좁은 320×568이다.
각 크기에서 라이트/다크를 확인한다. 모바일 크기 조절 결과와 실제 모바일 기기 결과는
구분해서 기록한다. 키보드만으로 메뉴·입력·표 스크롤·파일 선택까지 이동한다.

## 수동 검증표 — 전 항목 대기

아래 체크는 실제 수행하고 결과를 기록한 뒤에만 바꾼다. 자동 검사 통과로 채우지 않는다.

### 1. 작은·중간·큰 기록의 보기 전환

- [ ] 작은 기록의 Overview에서 Request map과 Retest map을 전환하고 요청/코드 상세가 맞는지 확인한다.
- [ ] 중간 기록은 API workspace의 Groups로, 50 API 또는 1000 HTTP 이상은 Distribution으로 시작하는지 확인한다. 49/50·999/1000 경계를 별도로 확인한다.
- [ ] Groups → API list → Distribution → 기존 보기로 왕복한다. 활성 버튼·페이지·선택 수가 실제 내용과 일치하고, 같은 보기 재선택은 현재 위치를 초기화하지 않는지 확인한다.

### 2. 사이드바·낮은 창·모바일 스크롤

- [ ] 낮은 창에서 사이드바 안을 스크롤해 마지막 메뉴까지 클릭하고 키보드로 접근한다. 선택 메뉴 표식과 메뉴 이름이 잘리지 않는지 확인한다.
- [ ] 모바일 줄바꿈 메뉴와 본문을 끝까지 이동한다. 사이드바·본문·표의 스크롤이 갇히거나 버튼을 덮지 않는지 확인한다.
- [ ] 긴 API/이력 표에서 머리글과 가로 스크롤을 확인한다. 다른 섹션으로 이동하면 본문은 맨 위로, 같은 보기 재선택은 기존 위치로 남는지 확인한다.

### 3. 히트맵 → 그룹 → API → 일치하는 요청

- [ ] 알려진 5분 UTC 구간의 셀을 눌러 시간·처리 시간대·건수를 확인하고 Groups → API list → Request map으로 이동한다. 요청 시각/시간대/API가 선택 범위와 일치해야 한다.
- [ ] 같은 시간 열 제목은 전체 처리 시간대를 선택한다. 빈 셀·Gap·미측정·4xx/5xx 표시와 누락 안내를 확인한다.
- [ ] 범위 내 상세가 없으면 관계도/초안 버튼이 비활성이고 누락 이유가 보이는지 확인한다. 범위 밖 최신 요청으로 대신 이동하면 실패다.
- [ ] 새 시간 범위는 선택·검색·상태·건수·p95 조건을 지우고 정렬·그룹 깊이를 유지한다. Reset filters는 시간 범위를 유지하며 All recorded time은 시간/처리 시간대 제한을 해제한다.

### 4. 필터·정렬·체크박스·선택 유지

- [ ] 검색·상태·최소 건수·p95·그룹 제한을 함께 적용하고 정렬 방향·빈 결과·페이지 수를 확인한다.
- [ ] API를 선택한 뒤 다른 페이지/보기/필터로 이동한다. 숨은 선택 수와 출처 사용 가능/누락 수가 맞고 Select current page가 해당 페이지만 변경하는지 확인한다.
- [ ] Clear group과 Reset filters의 범위를 확인한다. Reset filters 이후에도 API 선택·정렬·그룹 깊이가 유지되어야 한다.
- [ ] `GET /orders/1` 링크가 `/orders/10`이나 대소문자가 다른 API를 포함하지 않는지 확인한다. 직접 입력 검색은 부분 검색이며 `/`와 Esc가 현재 보이는 검색란에 적용되는지 확인한다.

### 5. 초안 편집·검토 해제·파일 다운로드

- [ ] Create drafts로 만든 초안에 실제 GET/HEAD 경로·기대 상태·선택적 client 시간 제한을 입력한다. 검토한 뒤 각 입력을 수정하면 검토가 해제되고 JUnit 다운로드가 비활성으로 돌아오는지 확인한다.
- [ ] 같은 API 출처로 다시 생성하면 중복 없이 편집 내용이 유지되는지 확인한다. 상세 누락 API와 POST는 실행 가능한 초안으로 잘못 안내하지 않아야 한다.
- [ ] JSON 초안·JUnit·API draft bundle을 실제로 내려받아 파일명·비어 있지 않은 내용·선택 API/범위를 확인한다. JSON 초안은 미검토 상태도 저장할 수 있고 JUnit은 검토가 필요하며 `@Disabled`를 포함해야 한다.
- [ ] 대시보드 HTML 다운로드를 확인한다. 원본 관측 리포트와 라이선스 고지를 보존해야 하며, 불러온 초안·실행 이력까지 영구 저장한 것으로 안내하면 안 된다.

### 6. 시나리오 저장·불러오기·잘못된 파일

- [ ] 빈 이름·미검토 사례의 오류 안내와 비활성 버튼을 확인한다. 검토 완료 후 Save scenario, Postman, disabled JMeter, local run command를 각각 실제 다운로드한다.
- [ ] 저장 파일을 다시 불러와 새 사례가 재검토 상태로 추가되고 기존 편집은 보존되는지 확인한다. 동일 출처 재불러오기로 중복을 만들지 않는지 확인한다.
- [ ] 잘못된 JSON·다른 kind·미지원 schema·1 MiB 초과 파일을 각각 불러온다. 오류가 보이고 초안·메타데이터가 보존되어야 한다. 같은 파일 재선택도 처리되는지 확인한다.
- [ ] Postman의 baseUrl은 비어 있고 JMeter 계획은 비활성인지 파일 내용으로 확인한다. 다운로드만으로 HTTP 요청을 실행하지 않아야 한다.
- [ ] 저장 후 새로고침하면 페이지 메모리 상태가 초기화됨을 확인한다. 파일 재불러오기로 복구하며 페이지 자체 저장으로 오해하지 않아야 한다.

### 7. 실행/관측 이력 선택·삭제·비교

- [ ] Run history에 서로 다른 2개 실행을 불러와 Current/Baseline을 고르고 실제 HTTP와 assertion 결과·client 시간을 구분한다. 조건·origin·표본·미완료 경고도 확인한다.
- [ ] Current 또는 Baseline을 Not selected로 바꾸고 검색·추가 import를 한다. 해제 상태를 유지하며 같은 ID 비교는 안내로 차단해야 한다. 검색은 목록만 좁히며 기존 비교 선택은 유지한다.
- [ ] 선택한 실행을 Remove loaded run으로 제거하면 다른 실행을 자동 선택하지 않아야 한다. 페이지에서만 제거되며 원본 디스크 파일은 유지되는지 확인한다.
- [ ] Recordings에서도 선택 해제 → 추가 import → 같은 ID 비교 → 선택 기록 제거를 반복한다. 서버 adapter 시간 비교와 Run history client 시간을 혼동하지 않아야 한다.
- [ ] 빈 목록·검색 결과 없음·잘못된 이력 파일·충돌 ID를 확인하고, Save loaded history/catalog의 실제 파일을 다시 불러와 내용이 맞는지 확인한다.

### 8. 긴 경로·빈 결과·키보드 초점·테마

- [ ] 긴 API 경로·그룹/시나리오/이력 이름을 표시한다. 줄바꿈·툴팁·가로 스크롤로 전체 내용을 확인할 수 있고 주요 버튼이 밀려 사라지지 않아야 한다.
- [ ] Tab/Shift+Tab, Enter/Space, 화살표로 메뉴·보기·정렬·체크박스·드롭다운·파일 선택·스크롤 영역을 사용한다. 초점 표시가 보이고 숨은 화면으로 이동하거나 갇히지 않아야 한다.
- [ ] 빈/legacy 기록·필터 결과 0건·상세 누락에서 명확한 안내와 다음 동작이 보이는지 확인한다.
- [ ] 라이트/다크에서 선택 메뉴·스크롤바·히트맵·오류·비활성 버튼·초점을 확인한다. 동작 줄이기와 강제 색상 설정도 해당 환경에서 확인하고 결과를 따로 기록한다.

## 결과 기록과 수정 범위

각 실패는 다음 형식으로 남긴다. 원본 개인 기록, 다운로드 파일, 서버 로그는 commit하지 않는다.

| 항목 | 기록할 값 |
| --- | --- |
| 식별 | 위 번호/하위 단계, 대상 commit, 검증 일시·검증자 |
| 환경/입력 | 브라우저·OS·창/기기·테마·합성 fixture 이름과 규모 |
| 재현 | 클릭/키 입력 순서, 기대 결과, 실제 결과, 재현 횟수 |
| 근거 | 민감정보를 제거한 스크린샷 또는 다운로드 내용 확인 결과 |
| 처리 | 최소 수정 범위, 관련 트러블슈팅 항목, 회귀 검사, 수정 commit, 같은 환경 재검증 |

실패가 확인되면 [25번 트러블슈팅](25_diagnostics_troubleshooting.md),
[35번 사용성 보완](35_dashboard_usability_review.ko.md), [41번 선택/비교 보완](41_workspace_followup.ko.md)을
먼저 참고한다. 시간 범위 변경과 일반 필터 초기화, 정확한 링크와 직접 검색,
Current/Baseline 해제 보존, 상세 누락과 집계 범위를 함께 회귀 확인한다.
이번에는 화면 문제를 재현하지 않았으므로 기능 수정·새 화면 이미지·UI 최종 승인은 없다.
머지·릴리스는 수행하지 않는다.
